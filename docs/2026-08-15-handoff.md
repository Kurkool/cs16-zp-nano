## What zp_damage_combo does now

A human earns an ammo pack two ways, and both are ours:

- **`zp_combo_damage 1000`** — one pack per 1000 damage dealt to zombies. A
  running total per player, not per zombie: 500 into one and 500 into another
  pays out. Survives death, respawn and the round boundary.
- **`zp_combo_kill_packs 1`** — one pack per zombie killed.

Three displays, in descending order of how much you can trust them:

1. **Chat line** — `[Combo] 1000 Damage -- +1 ammo pack (you now have 47)`,
   coloured, with the new balance. Cannot be lost. This is the one that made the
   feature work.
2. **Payout feed** — up to five lines centred at y 0.62, each naming its reason,
   each living 4 seconds.
3. **Progress block** — at x 0.82, counting in 100s and folding every five into
   a `+500 Damage!` line as the sixth lands, so it never exceeds five lines.

The zombie side is untouched: `zp_zombie_infect_reward 1` still pays a zombie for
infecting or killing a human, with no sound of its own. Do not add one.

## The thing worth knowing before you draw anything on screen here

This took the whole session and half a dozen rebuilds. **The client has four HUD
text channels, they are shared by every plugin on the server, and nothing can
reserve one.** `amxmodx.inc:659-665` says so plainly, including the warning that
a message meant to persist needs a fixed channel "to avoid possible flickering
due to auto-channeling".

Four channels, against these users:

| user | what it draws | how often |
|---|---|---|
| ZP status line | `HP ~ Class ~ Ammo Packs ~ Armor`, bottom left | **every 1.0s forever** — `set_task(1.0, "ShowHUD", ..., "b")` at `zombie_plague40.sma:2417`, holdtime 1.1 at `:8367` |
| ZP infect notice | blanked now, but still **holds a channel 5s** and is broadcast to everyone — `:5515-5520` | every infection |
| `zp_frost_m4a1` | freeze notice | on freeze |
| `zp_extra_bak47p` | a crosshair decoration, `:497` | every hit with that gun |
| us | feed + block | see below |

There is no way to add a fifth channel. The limit is a fixed array compiled into
the game client; raising it means modifying the client (MetaHook), which is a
different project and a VAC question on a Steam install.

**So the only rule that works: anything that must stay on screen has to be
redrawn faster than whatever is taking it.** We do not win the channel, we take
it back. A single ticker (`Task_Redraw`, 0.3s) is the only thing in the plugin
that writes to the HUD; it runs only while a display still has a live window.

Corollaries that each cost a rebuild to learn:

- **Never draw from the damage hook.** Doing so meant two HUD messages per damage
  event — twenty a second with a rifle, ten in a single frame when one Angelic
  stab hits five zombies. It cost visible frames. With the ticker as the only
  writer the message rate is fixed no matter how fast you fire.
- **Fade-in must be zero on anything redrawn.** A redraw kills the old message
  and adds a new one, and a new message fades from nothing, so a 0.1s fade
  against a 0.3s tick is the brightness dropping to zero three times a second.
  The progress block never flickered partly because it always had fade 0 - not
  only because it was redrawn often.
- **DHUD is not a bigger-font version of the same thing.** It is stack-based, 8
  deep, with no way to clear one message (`amxmodx.inc:741-744`). Redrawing a
  counter on it filled all eight slots with eight different values at once. And
  a DHUD message that arrives when the pool is full is *discarded*, which is why
  the payout announcement went missing while the reward sound - issued two lines
  later in the same function - played every time. That sound was the clue that
  the server side was never the problem.
- **The stack is shared too.** The trick of flooding eight blank DHUD messages to
  clear it would also wipe ZP's win announcements and the ghost countdown.

## The trade you are living with

Our two displays hold two of the four channels and take them back three times a
second, so **ZP's own status line flickers while `zp_combo_hud 1`**. This was
confirmed by switching it off: with our channels released, ZP's bar is perfect.

That is a deliberate choice - the payout centred on screen was worth more than
ZP's bar being steady, given the chat line means no payout is ever actually
missed. `zp_combo_hud 0` reverses it instantly and costs nothing but the visuals.

Merging both displays into one message on one channel was tried and helped but
did not fix it: the allocator can still hand ZP the one channel we hold. Getting
both means leaving the four-channel system, and there are two ways to do that.

**Entities and models**, the way `addon_floating_damage` and
`zp_addon_zbhealthbar` do - neither of which has ever flickered.
`models/x_re/floating_damage.mdl` is MDL v10 with four bodyparts of `blank` plus
digits 0-9 and **no letters**, so this route gives floating numbers, not words.

**DHUD, which deserves a second look and did not get one.** It is a separate
system from the four channels - `set_dhudmessage` has no channel parameter at
all - so moving our displays there would hand every channel back to ZP and
return the larger font at the same time. It failed earlier in the session for a
reason that no longer applies: back then the content changed on every redraw (a
`640/1000` counter), so the stack filled with eight *different* values at once.
The panel's content now changes rarely, and overlapping copies of identical text
at an identical position are the same pixels - invisible.

The condition is that holdtime must sit close to the tick interval so copies
never accumulate past eight; roughly tick 0.3 against holdtime 0.5 leaves one or
two live and six slots free for ZP's own DHUD messages. The failure mode is a
tick arriving after the previous copy expired, which shows as a flicker, and the
margin there is only 0.2s. Worth one experiment on its own revertible commit.

## Debug logging costs frames. All of it is off now

`log_amx()` writes the log file synchronously on the game thread. Several payouts
a second in a heavy fight produced a measurable frame rate drop with visible
hitching, and it vanished the moment `zp_combo_debug` went to 0.

Everything is 0 now, and each carries a comment saying why:

| cvar | file |
|---|---|
| `zp_combo_debug` | `zombieplague.cfg` |
| `zp_rules_debug` | `zombieplague.cfg` — writes on every death, same mechanism |
| `zp_angelic_debug` | `zombieplague.cfg` |
| `amx_debug` | `amxx.cfg` — the file's own comment warns "debug mode will affect JIT performance" |

Turn one on to investigate something, then turn it off before playing.

## Two ZP messages silenced without recompiling ZP

`NOTICE_VIRUS_FREE` and `NOTICE_INFECT`/`NOTICE_INFECT2` are blanked in
`data/lang/zombie_plague.txt`, `[en]` section only. **Blanking the text does not
free the channel** - ZP still calls `ShowSyncHudMsg` and still holds a slot for
five seconds, it just draws nothing. Stopping that needs the source changed, and
`zombie_plague40.sma` must not be recompiled: `zombieplague.inc` on disk is from
a newer ZP than the running plugin, so a rebuild is not guaranteed to reproduce
what is running.

## The tuning pass after the combo work

Same day, after the plugin was committed. Numbers only, plus one model swap - the
reasoning for each sits in a comment beside the value it explains, so this is just
the map of what moved.

**Zombie stats** (`zp_zombieclasses.ini`, every old value commented above its
replacement):

| | HP | gravity | knockback |
|---|---|---|---|
| Classic | 1800 -> 2000 | 1.00 | 1.00 -> 0.50 |
| Raptor | 900 -> 1100 | 1.00 | 1.50 -> 0.50 |
| Poison | 1400 -> 1600 | 0.75 -> 0.81 | 1.25 -> 0.50 |
| Big | 2700 -> 2900 | 1.00 | 0.50 |
| Leech | 1300 -> 1500 | 1.00 -> 0.81 | 1.25 -> 0.50 |

Knockback and gravity were set from CSCF's own class table
(`SUIC_CONFIG/SYSTEM/SUIC_NANO.RC`): it gives all twenty of its classes
`bearKnockBack 0.5` and separates them by health and gravity instead, with the
NURSE and GANGSI families at gravity 65 against everyone else's 80 - 65/80 =
0.8125, which is where Poison and Leech's 0.81 comes from.

**Two things to know about those numbers.** The `INFO` line on each class still
advertises `Knockback++` / `Knockback--` and is now lying: they are all equal.
And the HP bump moved two classes across a payout boundary, since a kill pays one
pack per `zp_combo_damage` of damage plus one for the kill - Classic at exactly
2000 now pays 3 instead of 2, and Raptor at 1100 crosses 1000 for the first time
and pays 2 instead of 1.

**Slowing without pushing.** `zp_knockback` was switched on to match CSCF and then
switched back off the same day, because what was actually wanted was a zombie that
slows when shot without being shoved off its line. That comes from
`zp_zombie_painfree 0` instead - pain shock is the engine's own per-hit slowdown
and that cvar only decides who is exempt from it, so 0 means nobody is, including
the last zombie alive that the old value of 2 was shielding. Note the two
interact: a pain-free zombie takes MORE knockback, so the old settings made the
last zombie both the fastest and the most easily thrown.

The per-class knockback values are dormant again while the master switch is 0 -
the state they were in for the whole life of the server before this - but they are
uniform now rather than the original spread, which matters if anyone flips it back.

**Poison is Gangsinano Master**, body and hands, replacing PSYCHO_HOST +
v_claw_ink. Neither model file is in git; both are described in
`zp_zombieclasses.ini`'s header along with the one lesson worth carrying:

> A Scene Root offset cannot be copied between models even when their skeletons
> are byte-identical, because it adds to geometry of a different extent. Aim at
> the finished bounding box. Every viewmodel that looks right on this server has
> its idle sequence starting at X ~3.6 and ending at Z ~-2.8.

That, and: `v_claw_corpsenano.mdl` had been sitting installed and unused, which
read as "ready" - it was not, its Scene Root was 0/0/0, and anything built on it
appears as a whole arm floating in mid-air.

**Ambience** now alternates between `cscf/bgm.mp3` and a new
`cscf/nano_ambience.mp3`, chosen at random each time one finishes. The source was
a 9.2 MB stereo 44.1 kHz WAV carrying six Pro Tools chunks; it was re-encoded to
mp3 rather than cleaned up, because ZP's `PlaySound` sends `.mp3` to the client's
media player and everything else to `spk`, and `spk` goes through the sample
loader that wants PCM mono 22050 and silently plays nothing otherwise.

**Bots** are at `yb_difficulty 4` (Expert - reaction 0.1-0.2s, headshot
probability 100%, through-wall attack chance 90). `yb_difficulty_auto` must stay 0
or bots quietly lower their own difficulty to balance team k/d. YaPB has no
zombie-mode support at all - no cvar in its config mentions zombies, and its map
prefix detection knows only `fy_` and `ka_`, not `zm_`. CS-EBOT was considered for
that reason and not installed; `addons/ebot/` is an empty stub.

## Settings that live only on this machine

`.gitignore:12` ignores everything at the repo root, so these are not committed
and will not survive a fresh clone:

- `listenserver.cfg` — `mp_roundtime 3`. Nothing had ever set it, so it was
  running on CS's default of 5. This is the round clock only; `zp_round_rules`
  still owns when a round actually ends, through `mp_round_infinite`.
- `listenserver.cfg` — `sv_rollangle 0`, no camera roll when strafing. **This is
  the one that works, and it has to be server side.** In multiplayer the client
  computes view roll from `movevars->rollangle`, which the server sends it, so a
  client's own `cl_rollangle` does nothing at all. `sv_rollspeed` stops mattering
  once the angle is 0.
- `userconfig.cfg` — `cl_rollangle 0`. Left in place, harmless, but it is NOT what
  fixed the tilt; see above. The file itself is worth knowing about: CS execs it
  after `config.cfg` and never writes to it, which makes it the right home for
  client cvars. Anything put in `config.cfg` is rewritten by the game on exit.

## How this session went wrong, and the two habits that would have saved it

Six or seven rebuilds went into a problem whose shape was visible early. Two
things caused that:

**Reading the include only after guessing.** Every hard fact that mattered was
one grep away in `amxmodx.inc` - four channels, the auto-channeling warning, DHUD
being a stack that cannot be cleared. Each was found *after* building something
that the documentation already ruled out.

**Abandoning a correct hypothesis because it was challenged.** The frame drop was
diagnosed correctly as log writes on the first guess, then dropped when it was
pointed out that logging had been on earlier too, and three more theories were
chased. Turning the cvar off would have settled it in ten seconds. When a
hypothesis is cheap to test, test it before arguing about it.

Two things worked, both from the last handoff's advice:

- **"What differs between the case that works and the case that does not."** The
  progress block never flickered while the payout message did, and the reason -
  one is redrawn constantly, the other written once - was the whole answer. It
  came from noticing that, not from reading code.
- **Turning a switch off to isolate.** `zp_combo_hud 0` proved in one round that
  we were the cause of ZP's flicker, after a long stretch of theorising about
  who was taking whose channel.
