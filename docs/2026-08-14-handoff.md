## The one thing that needs playing before it can be committed

`zp_damage_combo` grants a human one ammo pack per 1000 damage dealt to
zombies, shows the running total at the right of the screen, and announces the
payout with a sound and a `1000 Damage!!!` line near the bottom.

Written, compiles clean, installed, **never played**.

**The check that matters is not that the counter appears.** It is that one
completed combo grants exactly **one** ammo pack. Zombie Plague ships the same
reward (`zp_human_damage_reward`, `zombie_plague40.sma:2080`), and
`zombieplague.cfg` now sets it to `0` so this plugin can own the mechanic
instead — ZP has no native that exposes `g_damagedealt_human`, so the progress
cannot be read out of it and had to be re-implemented to be displayed. If that
cfg line is not taking effect, both accumulators run and packs arrive at double
rate, which looks like nothing at all until somebody notices the economy is
wrong.

Count packs before and after one full combo. Then confirm a zombie still gets
its `+1` on infection with no new sound — that path was deliberately left to ZP
(`zp_zombie_infect_reward`, `:2013`) and must not have grown a second owner.

Commit once it plays correctly.

## Zombie class models

All five classes have a matching body and claw set, drawn from two sources: the
CSCF Yasou 3.0 pack and `Mutant--Dread,assasin,hulk.rar`.

| Class | Body | Claw |
|---|---|---|
| Classic | `GHOST_NORMAL` | `v_claw_nano_ghost` |
| Raptor | `ASSASSIN_EVOLVE` | `v_claw_assassin` (MASTER arm + hook) |
| Poison | `PSYCHO_HOST` | `v_claw_ink` (INKUP, with hook) |
| Big | `HULK_NORMAL` | `v_claw_hulkfist` |
| Leech | `NURSE_EVOLVE` | `v_claw_nurse` (MASTER arm + hook) |

Spares are installed and switchable with one line each: bodies
`NANOINK_NORMAL`, `INK_ORIGIN`, `NURSE_ORIGIN`, `ASSASSIN_NORMAL`,
`HULK_EVOLVE`, `GHOST_EVOLVE`, `FURYGHOST_M_GR`; claw `v_claw_corpsenano`.

The long comment block at the top of `configs/zp_zombieclasses.ini` is the real
documentation. The short version — this pack has three separate ways to fail
and only one of them says anything:

- **MDL version 11 renders as nothing.** The player turns invisible while
  their health bar keeps floating. Twenty-five of the pack's sixty-eight bodies
  are v11, including every HULK and ASSASSIN. Flipping the version byte does
  not work; the file is encrypted past the header. Working HULK and ASSASSIN
  bodies came from the separate RAR, ported by Black_ranjau. **Look for a port
  before concluding a model cannot be used.**
- **A texture over 512 fails the map load** with `GL_LoadTexture: too big`. 512
  is not the true ceiling — `zombie_source` ships 516 and renders — but 1024 is
  past it, and thirty-one of the pack's claw models are 1024.
- **A bodypart whose first submodel has zero meshes renders nothing, silently.**
  `PV-ASSASSIN` hides its arm at submodel 1 behind a `blank` at 0, so at body 0
  you get a scythe floating with no arm attached. This one is the worst because
  the other two at least fail loudly.

Two tools in `tools/` handle the second and a related problem:

- `mdl_downscale.ps1` shrinks oversized textures. It is **not** an image
  resize: MDL stores UV coordinates in absolute texels, so halving a texture
  without halving every S/T on the meshes that use it makes the skin wrap
  rather than fail. It also only touches meshes whose `skinref` resolves to a
  texture actually being shrunk, because several models mix 512 and 1024.
- `mdl_offset.ps1` moves a viewmodel in view space by shifting its root bone,
  the only place that can move without breaking skinning. Ported CrossFire
  viewmodels sit far forward of where GoldSrc expects — `PV-ASSASSIN` started
  at X 22 where ZP's own `v_knife_zombie` starts at 3.7, which reads as an arm
  floating in mid-air rather than one entering from the screen edge.

Do not trust anything the pack calls itself. Internal model names are stale
metadata — `PV-HULKUP`, `PV-HULK` and `PV-NURSE` all report themselves as
`PV-NURSEUP.mdl` while being different files. Folder names lie too:
`CRAZYKNIFE` contains bare nurse hands, `INK` contains psycho textures.
`NURSE_ORIGIN` and `NURSE_EVOLVE` are byte-identical. Psyco and Nurse are the
same character with a different head.

## Custom M4A1 identity

`zp_extra_angelic_beast` and `zp_frost_m4a1` both hook `weapon_m4a1`. Both used
to keep a per-player bool and neither cleared the other's, so buying both left
both sets of hooks live on one weapon — a Frost-looking rifle with the
Angelic's 52-round clip.

Both now stamp `pev_impulse` with a unique key and gate every hook on the
entity. An entity holds one key, so two plugins can never both claim it and
neither has to know the other exists. A third M4A1 item could be added with no
changes to either. This was already the convention here —
`ak47_transformers_extra`, `zp_weapon_ak47_beast`, `zp_extra_bak47p` and
`zombie_plague40` all do it.

Identity now travels with the gun: drop an Angelic and it is still an Angelic
on the floor, and whoever picks it up gets one.

Three things that took real time and are easy to reintroduce:

- **Never strip the old weapon by hand.** `RemovePlayerItem` + `Item_Kill`
  destroys the entity while `m_pActiveItem` still points at it, and every later
  read of the player's weapon state is then looking at something that no longer
  exists. Use `engclient_cmd(id, "drop", ...)`, which is what pressing G runs.
  The symptom was having to drop manually and re-buy for the item to work.
- **`give_item()` deploys inside its own call.** The key has to be readable at
  the instant deploy runs, so either stamp before giving or run deploy again
  afterwards. `engclient_cmd` cannot stand in: CS ignores a select command for
  the weapon already in hand, which is the original bug in the first place.
- **`FM_SetModel` receives the weaponbox, not the weapon.** The box carries no
  key; the `weapon_m4a1` it wraps does. Asking the box is why a dropped Angelic
  wore the stock world model.

## Things that cost time to learn

- **`zombieplague.inc` is from a newer Zombie Plague than the plugin that
  runs.** The include declares eleven modes and natives such as
  `zp_get_user_sniper`; the running `zombie_plague40` knows seven modes
  (INFECTION, MULTI, NEMESIS, NONE, PLAGUE, SURVIVOR, SWARM) and registers
  thirty-seven natives, none of them those. A new plugin can call a native that
  does not exist, compile without a warning, and fail at run time. **Check any
  `zp_*` call against the `register_native` lines in `zombie_plague40.sma`, not
  against the include.** Knock-on: `zp_sniper_ignore_rewards` and
  `zp_assassin_ignore_rewards` in `zombieplague.cfg` are dead lines.
- **Check what ZP already implements before building a mechanic.** The damage
  reward and the infection reward both already existed and both worked.
- **ZP's admin player models override the zombie class model entirely**
  (`zombie_plague40.sma:5617`). With `ADMIN MODELS = d` and the only admin
  being the human player, every class model was being replaced by
  `ADMIN ZOMBIE = zombie_source` for that one player while the bots looked
  correct. Both admin-model cvars are off now.
- **WAV files from these packs need rewriting before use.**
  `nano3_wraithpoint_up.wav` was correct PCM (mono, 22050, 16-bit) but carried
  seven Pro Tools metadata chunks and a RIFF size field eight bytes short of
  the file. It is installed as a clean 44-byte-header PCM file. GoldSrc's
  failure mode for a WAV it dislikes is silence.

## How the bugs in this session were actually found

Every real defect came from a description of the symptom, not from reading
code. *"It is only my player, not the bots"* ruled out two plausible theories at
once and pointed straight at an admin-only feature. *"I have to press G and
re-buy for it to work"* exposed the dangling `m_pActiveItem` after three wrong
guesses at the cause.

When a guess fails twice, stop guessing and ask what differs between the case
that works and the case that does not.
