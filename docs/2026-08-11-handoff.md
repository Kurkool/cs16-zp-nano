## What the work was

The round-end gate itself — hold `mp_round_infinite` while a zombie can still
return, release it when none can — was built and verified by the previous
plan. This plan didn't change that behaviour; it changed the shape. Eight
sites used to write or recompute the flag, and only two of them could ever
run before a win check; three fix rounds on the old plan produced the same
class of bug three times, always a stale read caught mid-transition. This
plan collapsed all eight sites to one: a ReAPI pre-hook on
`CheckWinConditions` that computes the flag fresh, from a single predicate
asked the same way about every player, at the instant CS is about to read it.
There is no "right now" left to get wrong, because the value is never state.

## New dependency: ReAPI

`zp_round_rules.amxx` hard-depends on **ReAPI 5.29.0.358**
(`addons/amxmodx/modules/reapi_amxx.dll`, registered in `configs/modules.ini`).
`zp_round_rules.sma` includes `<reapi>` unconditionally, alongside
`<amxmodx>`, `<fakemeta>`, `<hamsandwich>` and `<zombieplague>` (:69-73), and
calls `RegisterHookChain(RG_CSGameRules_CheckWinConditions, "Gate_Pre",
false)` at `:214` and `rg_check_win_conditions()` at `:610` — there is no
`#if defined` guard anywhere in the file. Take the module away and AMXX has
no native to resolve either call to: the plugin fails to load. It does not
degrade to running gateless; it does not run at all.

ReAPI needs ReGameDLL, which this server already has (`dlls/mp.dll` is
ReGameDLL_CS 5.30.0.814); it does not need ReHLDS, because only game-side
hooks are used. It lives under `addons/`, which Steam's file verification
does not touch — unlike `dlls/mp.dll` and `delta.lst`, which it silently
reverts.

The hook chain enum is **`RG_CSGameRules_CheckWinConditions`**, named after
the *second* argument of the `LINK_HOOK_CLASS_VOID_CUSTOM_CHAIN2` macro that
declares `CheckWinConditions` at `multiplay_gamerules.cpp:881`
(`LINK_HOOK_CLASS_VOID_CUSTOM_CHAIN2(CHalfLifeMultiplay, CSGameRules,
CheckWinConditions)`) — not the `RG_CHalfLifeMultiplay_…` form the design
first guessed from the C++ class alone.

## Two coverage limits, stated honestly

**Case 6 could not be staged manually.** ZP swallows `chooseteam` and
`jointeam` for anyone already holding a team, dead or alive
(`clcmd_changeteam`, `zombie_plague40.sma:3124-3136`), and shows its own menu
instead — so the manual test the plan wrote is impossible by ZP's design, not
broken by this change. The caller is still exercised: ten bots joining teams
at map start each produce one gate line (`L20260812.log:17-26`, 00:12:36-42) —
that is `ChangePlayerTeam` (`multiplay_gamerules.cpp:5199`) firing, with
`zombies=0` and nobody dead yet, so `TeamExterminationCheck` cannot fire from
it either way. The coverage exists; the manual path does not.

**The `rg_check_win_conditions()` half of Task 3's fix is not exercised end
to end.** `allowed_respawn` (`zombie_plague40.sma:8765-8774`) refuses on
exactly four conditions — `g_endround`, `SPECTATOR`, `UNASSIGNED`, or the
player already being alive — and the spectator/unassigned routes are
unreachable for the same reason as Case 6. The only reachable refusal is
`g_endround`, which always coincides with `humans=0` and a round that has
already ended, so the `:888` guard inside `CheckWinConditions` makes the call
a no-op by design every time this server can reach it. Task 3 Step 5
(01:57:25-01:57:29) confirms the Critical fix at the level of the count —
`gate zombies=9 humans=0 dying=0 -> 0`, not 10, proving the refused player's
still-running task was actually dropped — but `bHold` needs `humans > 0` too,
so the line demonstrates no difference in `mp_round_infinite`'s output
between 9 and 10. The mechanism is established from source and confirmed by
review; the in-game demonstration stops one step short of the scenario a
mid-round refusal with `humans > 0` — that would exercise the win-check call
itself.

## Things that cost time to learn, this time

- **The ReAPI hook is named after the macro's second argument, not the C++
  class.** `LINK_HOOK_CLASS_VOID_CUSTOM_CHAIN2(CHalfLifeMultiplay,
  CSGameRules, CheckWinConditions)` at `multiplay_gamerules.cpp:881` produces
  `RG_CSGameRules_CheckWinConditions`, not `RG_CHalfLifeMultiplay_…`. Worth
  restating because the design document guessed wrong on the first pass and
  had to correct itself against the shipped `reapi_gamedll_const.inc`.
- **`CheckWinConditions` arrives in pairs on a death, but singly on a team
  join.** Every death event fires it twice within the same second (harmless —
  `Gate_Pre` is idempotent and cheap); bot team-joins at map start fire it
  once each. Do not read a duplicate `[RULES] gate` line as a bug, and do not
  assume every gate line has a twin.
- **A player already on a team, dead or alive, cannot reach CS's own
  team/spectate menu on this server.** `zombie_plague40.sma`'s
  `clcmd_changeteam` swallows `chooseteam` and `jointeam` and shows ZP's own
  menu instead. This is what closes off manual staging for two different
  verification cases above — worth knowing before writing a third one that
  needs the same menu.
- Everything in the previous handoff's list still holds: `CheckWinConditions`
  has exactly three callers and `Think()` is never one of them; ZP kills the
  last human rather than infecting them so the zombie-win branch has a corpse
  to fire on; `task_exists(id)` only searches the calling plugin's own tasks
  unless told `outside = 1`; never recompile `zombie_plague40.amxx`.
