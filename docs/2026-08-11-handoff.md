## What the work was

The round-end gate itself — hold `mp_round_infinite` while a zombie can still
return, release it when none can — was built and verified by the previous
plan. This plan didn't change that behaviour; it changed the shape. Eight
sites used to write or recompute the flag, and only two of them could ever
run before a win check; three fix rounds on the old plan produced the same
class of bug three times, always a stale read caught mid-transition. This
plan collapsed all eight sites to one: a ReAPI pre-hook on
`CheckWinConditions` that computes the flag fresh, from a single predicate
asked the same way about every player, at the instant CS is about to read it.
There is no "right now" left to get wrong, because the value is never state.

## New dependency: ReAPI

`zp_round_rules.amxx` hard-depends on **ReAPI 5.29.0.358**
(`addons/amxmodx/modules/reapi_amxx.dll`, registered in `configs/modules.ini`).
`zp_round_rules.sma` includes `<reapi>` unconditionally, alongside
`<amxmodx>`, `<fakemeta>`, `<hamsandwich>` and `<zombieplague>` (:71-75), and
calls `RegisterHookChain(RG_CSGameRules_CheckWinConditions, "Gate_Pre",
false)` at `:216` and `rg_check_win_conditions()` at `:558` and `:669` (the
final whole-branch-review fix wave added the first of those two calls — see
"Things that cost time to learn" below) — there is no `#if defined` guard
anywhere in the file. Take the module away and AMXX has no native to resolve
any of these calls to: the plugin fails to load. It does not degrade to
running gateless; it does not run at all.

ReAPI needs ReGameDLL, which this server already has (`dlls/mp.dll` is
ReGameDLL_CS 5.30.0.814); it does not need ReHLDS, because only game-side
hooks are used. It lives under `addons/`, which Steam's file verification
does not touch — unlike `dlls/mp.dll` and `delta.lst`, which it silently
reverts.

The hook chain enum is **`RG_CSGameRules_CheckWinConditions`**, named after
the *second* argument of the `LINK_HOOK_CLASS_VOID_CUSTOM_CHAIN2` macro that
declares `CheckWinConditions` at `multiplay_gamerules.cpp:881`
(`LINK_HOOK_CLASS_VOID_CUSTOM_CHAIN2(CHalfLifeMultiplay, CSGameRules,
CheckWinConditions)`) — not the `RG_CHalfLifeMultiplay_…` form the design
first guessed from the C++ class alone.

## Two coverage limits, stated honestly

**Case 6 could not be staged manually.** ZP swallows `chooseteam` and
`jointeam` for anyone already holding a team, dead or alive
(`clcmd_changeteam`, `zombie_plague40.sma:3124-3136`), and shows its own menu
instead — so the manual test the plan wrote is impossible by ZP's design, not
broken by this change. The caller is still exercised: ten bots joining teams
at map start each produce one gate line (`L20260812.log:17-26`, 00:12:36-42) —
that is `ChangePlayerTeam` (`multiplay_gamerules.cpp:5199`) firing, with
`zombies=0` and nobody dead yet, so `TeamExterminationCheck` cannot fire from
it either way. The coverage exists; the manual path does not.

**The `rg_check_win_conditions()` half of Task 3's fix needed correcting in
both directions, not just "not exercised end to end."** The 2026-08-12
whole-branch review went back to source instead of accepting the original
framing, and neither half of it survived unchanged.

The refusal path is almost certainly *unreachable*, not merely un-staged.
ZP sets `g_endround` in exactly one place — `zombie_plague40.sma:1605`,
inside `logevent_round_end` — and that function only runs off the
`Round_End` line ReGameDLL logs (`register_logevent("logevent_round_end", 2,
"1=Round_End")`, `zombie_plague40.sma:1130`). Every branch that ends a round
logs that line through `EndRoundMessage` and calls `TerminateRound` (which,
on the evidence available here, sets `m_iRoundWinStatus`) immediately after
it, in the same uninterrupted call — for example
`multiplay_gamerules.cpp:1377-1378`. That parenthetical is the one link in
this chain nobody can point to a line for: the vendored copy at
`.superpowers/sdd/2026-08-10-zp-round-rules-plan/regamedll-
multiplay_gamerules.cpp` has `TerminateRound`'s 17 call sites, each passing
an explicit `WINSTATUS_*` constant, but not the function's own body, so the
assignment itself is inferred from the call signature and the reads of
`m_iRoundWinStatus` elsewhere in the same file, not read directly. No
AMXX-scheduled callback, `Task_Respawn` included, can run in the gap
between those two statements either way, so by the time anything this
plugin schedules can observe `g_endround == true`, `m_iRoundWinStatus` is
already set too, on that same inference. That makes
`m_iRoundWinStatus != WINSTATUS_NONE` — the `:888` guard's condition —
*guaranteed* whenever `allowed_respawn()` refuses because `g_endround` is
set. Causation, not the coincidence the original wording implied.

The success path is a structural no-op too, which nobody had previously
said: a dead player with a pending `TASK_RESPAWN` (`zp_round_rules.sma:356`)
and an alive zombie (`:353`) score identically in `WillCountAsZombie`, so a
*successful* respawn changes no count either — there is nothing for a win
check to react to.

Where the call is genuinely load-bearing is a path nobody had reasoned about
at all: a respawn that lands the player as a **human** rather than a
zombie.
- `Task_Respawn`'s give-up-after-retries branch says so out loud —
  `"gave up waiting on zp after %d retries - respawning anyway, may hold a
  gun"` (`zp_round_rules.sma:600`). If `zombie_plague40.sma`'s `g_newround`
  is still `true` at that moment, `fw_PlayerSpawn_Post`'s gate (`:1795`,
  `if (g_respawn_as_zombie[id] && !g_newround)`) skips the *entire*
  `zombieme()` call, not just a weapon strip inside it — the player falls
  straight into the human spawn path a few lines below instead. They go
  from counted-as-zombie (a pending task) to counted-as-human in one
  respawn.
- ZP's own respawn timer reaches the same outcome through a different
  door: `zp_respawn_on_worldspawn_kill` arms `respawn_player_check_task`
  2.0s after every spawn (`zombie_plague40.sma:1791-1792`), on a timer that
  runs whether or not this plugin is watching. A death landing in the gap
  between that fixed 2.0s mark and `zp_rules_respawn_delay` lets ZP's own
  check win the race: it force-respawns the player through
  `respawn_player_manually()` with `g_respawn_as_zombie` set from whatever
  team they were on **at death** (`zombie_plague40.sma:7501-7504`), so a
  dying human comes back human. `Task_Respawn`'s stale-task skip branch
  (`zp_round_rules.sma:514`) then finds `is_user_alive(id)` already true
  and removes its own now-redundant task; without the call at `:558`, that
  return would quietly move the player from the zombie side of the count
  to the human side with nothing else watching for it.

Neither of these was staged in game — both are rarer than the cases that
were — but both are reachable without ZP blocking anything, which is more
than could be said for the spectator/unassigned routes. Task 3 Step 5
(01:57:25-01:57:29, `gate zombies=9 humans=0 dying=0 -> 0`) still stands as
confirmation that the count itself is right; it was never evidence about
which refusal reason matters, because that question was never asked before
now. The call earns its place — just on a path this project had not looked
at.

## Things that cost time to learn, this time

- **The ReAPI hook is named after the macro's second argument, not the C++
  class.** `LINK_HOOK_CLASS_VOID_CUSTOM_CHAIN2(CHalfLifeMultiplay,
  CSGameRules, CheckWinConditions)` at `multiplay_gamerules.cpp:881` produces
  `RG_CSGameRules_CheckWinConditions`, not `RG_CHalfLifeMultiplay_…`. Worth
  restating because the design document guessed wrong on the first pass and
  had to correct itself against the shipped `reapi_gamedll_const.inc`.
- **`CheckWinConditions` arrives in pairs on a death, but singly on a team
  join, and the 2026-08-12 whole-branch review finally found out why.** Every
  death event fires it twice within the same second (harmless — `Gate_Pre` is
  idempotent and cheap); bot team-joins at map start fire it once each. The
  reason: `CBasePlayer::Killed` calls `CheckWinConditions()` directly, in
  addition to the path this project already knew about -
  `PlayerKilled` -> `DeathNotice` -> `CheckWinConditions()` at
  `multiplay_gamerules.cpp:4185`. ReGameDLL's own comment two lines above that
  call says as much: `// TODO: It is called in CBasePlayer::Killed too, most
  likely, an unnecessary call. (Need investigate)`. A death goes through
  `Killed` and trips both paths; a disconnect or a team change goes through
  neither, so it only fires once. Do not read a duplicate `[RULES] gate` line
  as a bug, and do not assume every gate line has a twin.
- **A player already on a team, dead or alive, cannot reach CS's own
  team/spectate menu on this server.** `zombie_plague40.sma`'s
  `clcmd_changeteam` swallows `chooseteam` and `jointeam` and shows ZP's own
  menu instead. This is what closes off manual staging for two different
  verification cases above — worth knowing before writing a third one that
  needs the same menu.
- Everything in the previous handoff's list still holds, with one correction:
  `CheckWinConditions` has **four** callers, not three (see above), and
  `Think()` is still never one of them. ZP kills the last human rather than
  infecting them so the zombie-win branch has a corpse to fire on;
  `task_exists(id)` only searches the calling plugin's own tasks unless told
  `outside = 1`; never recompile `zombie_plague40.amxx`.
