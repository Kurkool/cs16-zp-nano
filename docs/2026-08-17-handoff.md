## The thing to understand before touching these guns again

**The Angelic's bullet holes were never where its bullets went.**

`DrawBulletHole` traced a line straight out of the eye along `pev_v_angle` with no
spread applied and stamped a decal at the endpoint. The holes marked where the
player was *aiming*. That is the entire reason the gun read as pinpoint accurate,
and the Iron Beast was a byte-identical copy.

Two things follow, and the second one matters more:

- The gun was never more accurate than a stock M4A1. Only its feedback was.
- **Nobody could ever have verified that pinning `m_flAccuracy` worked**, because
  the evidence they would have read was fabricated. The comment in both plugin
  headers saying "accuracy is pinned" has never been tested. It is still in the
  code and still unproven.

Both guns draw at the real trace endpoints now. `zp_angelic_decal_real 0` and
`zp_ironbeast_decal_real 0` restore the old behaviour instantly. Expect both to look
noticeably less accurate than they used to — that is the truth becoming visible, not
a regression.

The AT15 had a second copy of the same illusion from the other direction: it replayed
its fire event `FEV_HOSTONLY`, so the *client* drew its own spread-accurate holes
from prediction. Any server-side accuracy experiment was invisible on screen. The
event is dropped entirely now, which also stopped the stock galil report burying the
pack's own fire sound.

## Bullet spread is controllable now, and it is not CrossFire's model

All three guns take `zp_*_spread_scale`, applied through a ReGameDLL
`RG_CBaseEntity_FireBullets3` hook that multiplies `vecSpread` — the cone the engine
is about to fire with. Arg 4, and it is a scalar here, not the `Float[3]` that
`FireBuckshots` takes.

**Do not read this as a port of the Prism Beast.** CrossFire controls spread with
`moderator 0.5` and `resetTime 0.3`, an accuracy-*recovery* model, and the RC gives
those two numbers without the formula behind them. CS has no equivalent concept —
`m_flAccuracy` only ever grows while the trigger is down, there is no decay — so
there is nothing to map them onto. The `0.5` shipped on all three guns is a chosen
value. `moderator` also being `0.5` is a coincidence between two unrelated
quantities and has caught me out once already.

What *is* matched exactly: all 28 `kickback_*` numbers, `intervalTime 0.070`,
`deployTime 0.81`.

Open, and deliberately deferred until the pile has been played: modelling the
recovery behaviour — scale the cone by time since the last shot instead of a flat
number. That would be an interpretation of `moderator`/`resetTime`, not a port, and
adding a guessed formula on top of a batch nobody has fired yet would make it
impossible to tell what works.

## Identity belongs to the weapon, not the player

The AT15 pack held ownership in `g_has_aks74u[]` and stamped `pev_impulse` only while
the gun sat on the ground, **clearing the key again on pickup**. So a held weapon
carried no mark at all and every stat keyed off a per-player bool. Any path that lost
the weapon without producing a galil weaponbox left that bool set, and the next plain
galil the player touched inherited the damage multiplier, the recoil table, the
42-round clip and the spread scale.

The key is set once now and never cleared. `Is_AT15(ent)` is a property of the entity
in front of you: hold a galil, get galil stats. `za_ru_lavam4a1` got the same
treatment — it hijacks `weapon_galil` too, and its flag survived a drop, so a dropped
120-pack FrozenLava could come back off the ground as a 43-pack AT15.

Ownership rule, now identical across the family: **lost on infection, connect,
disconnect and drop — kept across rounds and across dying as a human.** Dying no
longer erases it; the gun on the ground is still itself and whoever picks it up gets
it. `za_ru_lavam4a1`'s `Death()` used to clear its flag *before* the corpse's
weaponbox was modelled, which destroyed the identity on the single most common way
the weapon changes hands.

## `give_item` does not enforce the one-primary rule

Four plugins dropped only their own base weapon before calling it. Hold an AT15,
which is a galil, then buy the Angelic, which is an m4a1: nothing to drop, and you
walk away carrying two primaries. Every purchase path drops all primaries now, using
`engclient_cmd "drop"` — the mechanism was already right and documented, only its
scope was too narrow.

`Scar_Born_Beast` and `yt_weapon_balrogm4_0` have the mask but were **not read** to
confirm they use it on purchase. The three ak47 plugins have not been looked at.

## Timing that was inherited rather than measured

`STAB_DELAY 0.85` in both M4A1 guns is CrossFire's **Born Beast** number, not the
Prism Beast the rest of these guns match. Measured off the models:

| | stab animation | was locked | input returned early by |
|---|---|---|---|
| Angelic | 67 frames @ 100fps = 0.670s | 0.85s | 180ms |
| Iron Beast | 267 frames @ 500fps = 0.534s | 0.85s | 316ms |

Both mouse buttons were dead that whole time, with the hands already back on the
gun. Cvars now: the Iron Beast gets the Prism Beast's own `0.55`, which its animation
fits inside with 16ms to spare; the Angelic's animation is *longer* than 0.55 so its
own length is the floor at `0.67`. **Re-time either model and its cvar has to
follow** — `check_reload_timing.ps1` only walks reload sequences and will not catch
this one.

## reapi is now load-critical for four plugins

`modules.ini` is one line: `reapi`. Depending on it, with no `#if defined` guard and
no `set_native_filter`, are `zp_round_rules`, `zp_extra_angelic_beast`,
`zp_extra_ironbeast` and `cso_at15hw`.

If that module ever fails to load — an AMXX update, a bad `.dll`, someone editing
`modules.ini` — **three guns disappear from the extra items menu and the round-end
gate dies with them.** AMXX resolves natives at plugin load and rejects the whole
file, it does not skip the call. Each of the three logs a line if its hook fails to
attach, so check `addons/amxmodx/logs/` and `amxx plugins` first if anything looks
wrong.

## Two habits that paid, and one trap

**Read the model, not the waveform, for animation timing.** These CrossFire
viewmodels carry the animator's own studio events — id 5004, a frame number, a WAV
name — so `frac = frame / numframes` is exact. The waveform still matters, but only
to decide whether a transient correction is needed on top: the Angelic's sounds all
peak inside 0.05s and need none, while the Iron Beast's magin peaks at 0.08s with a
second of glass tail and carries a deliberate +0.05.

**A control that should pass is worth as much as the failing case.** The reload
checker had the Iron Beast in it from the start, and it passing in the red run is
what proved the checker itself worked. Same with searching a compiled `.amxx` for a
cvar that is known to exist before trusting an ABSENT result — the first search said
absent for everything, including a cvar that demonstrably works, because AMX stores
string literals one character per 32-bit cell.

**`amxxpc` is not byte-reproducible.** The tail of the image varies between runs —
usually the last couple of bytes, once a ~750-byte region carrying leaked heap
content. So "installed hash != fresh compile hash" does **not** mean the wrong build
is installed. Inflate both and diff; if the only differences are past the code and
data, they are the same build. Also: `amxxpc -o"name"` writes nothing at all while
still printing the size table, "Done." and exit 0.
